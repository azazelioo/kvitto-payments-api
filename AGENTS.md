# Правила разработки

Это инструкции для дальнейших этапов, а не перечень уже реализованных функций.

## Источник требований и scope
- Следовать PDF «Тестовое_Junior_Python_FastAPI.pdf»; отличать требования PDF от согласованных решений.
- Реализовывать только текущий порученный этап небольшими проверяемыми изменениями.
- Не добавлять фронтенд, авторизацию, реальную интеграцию с банком и деплой.

## Деньги
- Все суммы в API и БД хранить и рассчитывать в целых копейках; float запрещён.
- amount — итоговая сумма после скидки; discount — размер скидки в копейках (согласованное решение).
- KVITTO10 даёт скидку 10% и нечувствителен к регистру; неизвестный код — 422.
- График рассчитывать через divmod: остаток распределять по первым платежам; сумма графика точно равна amount.

## Контракт API
- Сохранять поля ответов и HTTP-коды из PDF; ошибки валидации — стандартные FastAPI 422.
- Запрещённый переход: ровно 409 {"error": "invalid_transition"}, без detail; запись не изменяется.
- Успешный вебхук: 200 {"result": "ok"}.
- Разрешать только pending → succeeded, pending → failed, succeeded → refunded; новый платёж — pending.

## База и конкурентность
- Использовать SQLAlchemy 2 и отдельную Session на запрос; гарантировать закрытие. Транзакциями управляет бизнес-логика, без автоматического commit в зависимости.
- После IntegrityError выполнять rollback; не маскировать посторонние ошибки БД под идемпотентный повтор.
- Создавать схему через Alembic, без create_all в приложении; не подключаться к БД при импорте.
- Защищать idempotency_key уникальным ограничением БД с учётом конкурентных запросов.
- Повтор ключа возвращает тот же платёж с 200, в том числе при другом валидном теле; невалидное тело даёт обычный 422 (согласованное решение).
- Переходы статусов защищать условным обновлением в БД. Не применять конфликтующий вебхук автоматически к новому статусу без явно согласованного правила.

## Подпись вебхука
- Вычислять HMAC-SHA256 от исходных байтов тела с секретом из WEBHOOK_SECRET; сравнивать через hmac.compare_digest.
- При заданном секрете отсутствующая или неверная X-Signature — 401.
- При пустом секрете проверка отключена; документировать это поведение (согласованное решение).

## Проверки
- Использовать отдельные временные БД; проверять суммы, содержимое ответов и состояние БД.
- После изменения кода выполнять из корня репозитория:
  - .venv/bin/python -m pytest
  - .venv/bin/ruff check .
  - .venv/bin/ruff format --check .
- Не скрывать предупреждения без выяснения причины. Успешными называть только выполненные проверки; явно указывать невыполненные проверки и причины.

## Работа с репозиторием
- Не добавлять токены, пароли, .env, .venv и локальные БД в Git.
- Не выполнять разрушительные команды и force push; коммит и push — только по явному поручению.
- Не перезаписывать несвязанные изменения пользователя.

## Общение и AI_LOG
- Объяснять решения понятным языком; после этапа перечислять изменения, проверки и ограничения.
- AI_LOG.md заполнять только фактическими сведениями; не придумывать название модели, ошибки и действия пользователя.
- Предпочитать простую структуру без ненужных абстракций.
